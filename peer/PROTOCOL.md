# Ares Peer local protocol (v1)

Dependencies: `zeroconf==0.151.3`, `websockets==17.1`, Python 3.14. Start with `python -m peer serve --bind 0.0.0.0 --port 9431`. The daemon is **not** installed or started by importing this package. Default state and control socket: `~/.local/share/ares-peer` and `~/.local/share/ares-peer/control.sock`; `ARES_PEER_STATE` overrides the directory. **Installer must make the existing directory mode 0700** before launch (it may already contain the venv and be mode 0755). The socket and identity/state files are 0600. Never copy state between hosts. The `serve` entrypoint wires the local read-only `LocalSource` provider to `~/.hermes/state.db` and `~/.config/herdr/herdr.sock`, with a separate read-only `SessionBinding` proof over the active lease and exact Herdr process identity. If either source is absent/incomplete, remote calls fail closed. A terminal may be observed without a proven session ID; the service does not invent ownership. No remote data is sent before authentication. Tests can inject a stub provider without touching live data.

Stable CLI: `python -m peer status|arm|discover|pair <discovered-peer-id> <source-local-fingerprint> <alias>|revoke <alias-or-peer-id>|inventory <alias>|sessions <alias> [--profile P --limit N --offset N]|read <alias> [--lines N --max-bytes N]`. For `read`, pipe a JSON target object, e.g. `{"target":{"socketPath":"...","paneId":"...","tabId":"...","terminalId":"...","agentKind":"..."}}`, to stdin (not argv). `pair` prompts on an interactive coordinator-local TTY for the code; neither code nor token is placed in argv, and no secret appears in `status`. Run `arm` on the **source local console** and compare the source's `status` fingerprint independently; mDNS's fingerprint is untrusted and cannot substitute for this check. Pair only after `discover` on the running coordinator service. The `arm` code prints only to that source console. No control/input/attach operation exists.

## Owner-private Unix socket (one JSON line per connection)

A request must be at most 16,384 bytes including JSON (newline excluded); a response may be up to 262,144 bytes because a busy host's complete inventory carries hundreds of bounded terminal records. Timeout 10 seconds. Responses always use `{"ok":true,"result":{...}}` or `{"ok":false,"error":"denied|unavailable"}`. Request examples:

- `{"op":"status"}` → `result` has `peer_id`, `fingerprint`, `trusted` aliases, `authorized` peer IDs, no secrets.
- `{"op":"arm"}` → `result` has `code` (8 decimal digits, valid for 120 seconds), `fingerprint`; source owner only.
- `{"op":"discover"}` → `result.peers` entries contain `id`/`peer_id`, `alias`, `paired`, `online`, `name`, `address`, `port`, `fingerprint`. Paired peers missing from current mDNS are still listed with `online:false` and their local alias. `online` indicates a matching current *announcement*, **not** authenticated TLS reachability; no authorization follows from it. A mismatched fingerprint announcement for a paired ID is marked offline. All announcements are untrusted; no token is returned. Calling discover caches endpoint metadata for the subsequent pairing attempt in this running process.
- `{"op":"pair","peer":"<discovered-id>","fingerprint":"<64 lowercase hex verified at source>","code":"<source-local-code>","alias":"node"}` → `result` contains `peer`, `peer_id`. The Rust HTTP adapter may send `peerId` instead of `peer`; exactly one key is accepted. Peer IDs are 32 lowercase hex and codes exactly 8 decimal digits. The coordinator checks the presented TLS certificate pin **before** transmitting the code. Pairing requires a locally armed source code, expires and rate-limits; duplicate local aliases fail closed.
- `{"op":"revoke","peer":"node"}` → `result.revoked`. Run on the **source** with the coordinator peer ID to invalidate its bearer token; run on the coordinator with its source alias to forget local trust. Do both to clean up both sides.
- `{"op":"rpc","peer":"node","request":{"op":"inventory"}}` → only after token authorization and a complete local source snapshot, `result` contains `{"ok":true,"terminals":[...],"errors":[],"complete":true}`. `request.op` may instead be `sessions` (optional `profile`, `limit`, `offset`) or `read` (required exact `target`, optional `lines`, `max_bytes`). Provider failure returns `{"ok":false,"error":"unavailable"}`; never return fake terminals or an sshTarget. Never infer a pane/session binding or owner from titles, hostname, or a conflicting registry.

## Source-local write-grant state (wire input disabled in serve)

A source-owner pin is accepted only from an exactly mode-0600 regular file in an owner-only state directory with non-symlinked, non-group/world-writable ancestors. These checks are necessary but **not sufficient** for write origin. Linux `SO_PEERCRED` captures peer credentials at connect/listen time, while pathname `lstat` identifies the current directory entry; neither binds the connected stream to the validated listener. A same-UID process can transiently replace that entry and fork a responder while a process executing the pinned binary supplies the apparent PID. `fstat` on the connected client socket does not yield the listener's pathname inode either. The checkout deliberately returns no positive origin and never publishes a `terminalGeneration` from `LocalSource`, even with a configured pin. Legacy read-only inventory and observation remain available. Do not enable source-local grant or network writing until a source-authenticated, independently verified binding primitive and installed Herdr fence are provided.

`python -m peer write-grant <32-lowercase-hex-paired-peer-id> <profile> <session-id> <terminal-id> allow --ttl 60` is a **source-owner-local** request to the private Unix control socket, not a remote RPC. `deny` with the same arguments withdraws consent. The exact JSON request is `{"op":"write_grant","peer":"<id>","profile":"default","session_id":"<id>","terminal_id":"<id>","allow":true,"ttl":60}`; `ttl` is 1–300 seconds. Only the running source process holds this grant in memory; restart, re-pair and revoke erase it. Consent does not follow from pairing or observation. One peer at a time may own a write grant. A future implementation would require a unique, complete, independently verified Hermes owner matching Herdr's `agent_session`, an independently attested connected-listener origin, the independent process/lease proof and **both** source-authenticated `session.snapshot` fields: top-level `snapshot.server_instance_id` (new for every Herdr server process) and each pane's `runtime_generation` (new for every PTY runtime incarnation, including restore/relaunch with reused pane/terminal IDs). These nonempty bounded IDs come only from the allowlisted source-local Herdr socket, never the grant request, pane/process inference, or the peer wire. The proposed write generation hashes these proofs, but the current checkout cannot establish connected-listener origin and therefore cannot grant. A future implementation must recheck across snapshots and every availability query. Missing, invalid or stale attestation refuses a grant without blocking read-only observation/preview. **Stock Herdr v0.9.1 does not emit these fields, so local write grants remain unavailable until an authenticated patched Herdr server implements this snapshot contract.** Herdr may preserve terminal IDs across server restart; those IDs alone are never a generation. **The installed `serve` entrypoint does not construct a writer or set `enable_writer=True`; grants alone cannot activate input.** The checkout has an explicitly injected, default-off `PeerServer(writer=..., enable_writer=True, writer_peer_id=..., writer_cert=..., writer_pin=...)` test boundary only. The TLS server trusts the pinned peer certificate as an optional client certificate, and a writer requires that exact certificate, exact configured peer ID and valid bearer before a source-local grant can be consumed; certificate absence never downgrades to bearer-only control. The source operator must separately attest the installed Herdr patch and every competing input/lifecycle fence before any deployment or live enablement. Grant state alone must never be construed as permission to start a second Hermes writer.

## Remote wire

TLS WebSocket; read RPCs remain one JSON request/response per connection. Source announces `_ares-peer._tcp.local.` TXT with ID and fingerprint as **hints only**. On the wire, `pair` sends `{op,peer_id,code}`, other requests send `{op,peer_id,token,args}` where read `op` is one of `inventory`, `sessions`, `read`, `preview`, `history`, `observe`. The source stores only SHA-256 bearer-token hashes and checks in constant time. Source refuses read operations before authentication. The client verifies stored certificate pin before sending any code or token, even on reconnect. Requests are bounded at 16,384 bytes and responses at 262,144 bytes; WebSocket compression is disabled and operations have deadlines. The local provider is read-only and may refuse incomplete Herdr snapshots or conflicting session ownership. An authenticated, independently source-authorized `observe` RPC returns one bounded base64 output-only frame after fresh owner checks; pairing alone never grants observation. Ordinary read-only clients reject all input methods.

`history` is authenticated read-only display history: `{"profile":"<exact>","session_id":"<exact>","limit":8,"before":<positive integer>}` (omit `before` for the newest page). The result is `{"messages":[{"role":"user|assistant","text":"<at most 500 characters>","cursor":<display_order>}],"next_before":<oldest returned cursor or null>,"has_more":<boolean>}`. Pages are chronological, at most eight messages, and the whole response fits 16,384 bytes. Pass `next_before` to move older; a null cursor ends pagination. Missing display index/backfill, hidden or unmatched sessions fail closed; archived sessions remain readable. No input, transcript hydration or terminal ownership is implied.


**Checkout-only coordinator broker (not wired by `python -m peer serve`):** Tests may inject `ControlBroker(state)` into `LocalControl(state, broker=...)` on the coordinator. The owner-private `control.sock` accepts one JSON line per connection, up to 16,384 bytes (newline excluded), with exact fields:

- `{"op":"control.begin","peer":"<exact trusted alias or peer ID>","profile":"default","session_id":"<source session>","terminal_id":"<source terminal>","ttl":10}` → `{"ok":true,"result":{"handle":"<64 lowercase hex>","sequence":0}}` only after verifying the saved source certificate pin over mTLS and obtaining the source's sequence-zero acknowledgment. `ttl` is 1–300 seconds and bounds the coordinator handle only; source consent expiry independently gates each input.
- `{"op":"control.send","handle":"<opaque handle>","peer":"<same alias>","profile":"default","session_id":"<same session>","terminal_id":"<same terminal>","sequence":1,"text":"one line"}` → sequence-only acknowledgment. Input is nonempty, <=2048 UTF-8 bytes, no control characters. Never retry after a missing acknowledgment.
- `{"op":"control.release","handle":"<opaque handle>","peer":"<same alias>","profile":"default","session_id":"<same session>","terminal_id":"<same terminal>","sequence":2}` → sequence-only acknowledgment after source-confirmed release; this is not application-level receipt.

For a successful `control.begin` or `control.send` response, the same local Unix connection **must** send a second frame `{"op":"control.ack","handle":"<returned or supplied handle>","sequence":N}` within two seconds and read `{"ok":true,"result":{"ack":true}}` before closing. This is only the caller's assertion that it received the response on that connection; it cannot prove the caller actually read or processed the payload, nor application-level receipt of input. Missing, malformed or late receipt closes the remote socket and permanently quarantines that source binding for this broker lifetime; an ambiguous send must never be retried, even if the first response was locally visible. Cancellation while the source RPC is pending reaps the operation and quarantines any handle it produced; cancellation during local response drain leaves the ACK unconfirmed and fences the binding. `control.release` needs no second frame: its source-confirmed release is retained as an idempotent receipt for the exact UID, alias, source target, trust snapshot and sequence, until the handle TTL (at most 300 seconds); receipts are capped at 256 and never authorize writing. If local receipt confirmation is lost, treat the operation as uncertain, not as permission to retry input.

The broker binds the CSPRNG handle to the exact trusted peer ID, alias, URL, pin and bearer snapshot; source profile/session/terminal; local Unix UID; monotonic TTL; and next sequence. It never writes the handle, bearer or input to disk and never returns terminal frames. Changed trust, replay, invalid binding, local disconnect, remote EOF, timeout, or shutdown attempts to close the WebSocket and quarantines an uncertain binding in memory until broker restart; only an acknowledged release clears the binding. Shutdown first stops admission and detaches every handle, then cancels and waits for in-flight begin/send coroutines (including their cleanup) before `ControlBroker.close()` returns successfully. That return is the **completed broker-coroutine fence**: no broker send coroutine remains able to enter a WebSocket send after it. A send already in progress may have delivered input before that fence; neither return nor a WebSocket close proves that no input reached the source or application. If a cancellation-resistant send cannot settle within the bounded wait, `close()` raises `control shutdown incomplete`, retains binding and transport quarantine, and MUST NOT be reported as successful shutdown or used to authorize another writer. A failed/cancelled socket close likewise leaves an explicit quarantine holding the transport reference and binding fence; transport closure is not claimed. A restart does not resurrect a handle or replay a send, and source-side single-use consent prevents reconnect replay. The source writer remains disabled in normal `serve`; neither these fake-only tests nor the broker authorize installed Herdr input.
**Checkout-only fake-injected source writer protocol (disabled in `serve`):** On one authenticated TLS WebSocket, send `{"op":"control.begin","peer_id":"<paired-id>","token":"<token>","args":{"profile":"default","session_id":"<id>","terminal_id":"<id>"}}`. Exact keys only: no client-supplied server epoch, generation, socket, pane, or lease. After an unconsumed owner-local grant and positive no-takeover `ControlTerminal` acquisition, the only response is `{"ok":true,"result":{"sequence":0}}`. Then `control.send` with the same peer/token and `args:{"sequence":1,"text":"<single-line UTF-8>"}`; every subsequent sequence must increment exactly by one. Text is nonempty, no control/newline characters and <=2048 UTF-8 bytes. `control.release` has only `args:{"sequence":N}`. Acknowledgments contain only `sequence`; no terminal frame, socket, token or identity is returned. Each frame is <=16,384 bytes. Failed authentication, malformed/replayed/out-of-order input, revoked/expired grants, changed verified owner, TLS disconnect or idle timeout closes the controller. A grant is consumed **before** acquisition; a dropped send acknowledgment is ambiguous, so **never retry the send**. Reconnect needs fresh source-local consent, preventing a duplicate sequence from executing across sockets. Release does not imply application-level receipt by Hermes. No attach/SSH fallback exists. This experimental boundary does **not** prove Herdr's installed competing-input fences or live suitability.
